# 検証計画: Lambda Web Functions × Aurora DSQL

何を、なぜ、どう測るか。構成と運用は [architecture.md](architecture.md)、実機で確かめた事実は [findings.md](findings.md)、Web Functions の仕様と出典は [web-functions-notes.md](web-functions-notes.md)。リージョンは ap-northeast-1。

## 1. 目的と仮説
Aurora DSQL をバックエンドにしたときの、レイテンシ・スループット・コストを、Event Functions + 関数URL と Web Functions で比較する。

仮説: Web Functions は 1 つの実行環境で複数リクエストを同時に処理するので、DSQL の接続プールを共有できる。その結果、
1. 接続確立のコスト（TLS + IAM 認証トークンの生成）が減り、レイテンシが下がる
2. DSQL 側の接続数と接続レートが大きく減る
3. I/O 待ちの間は CPU 課金がほぼ発生しないので、DB 待ちが長いほどコストが有利になる

反証される場合も想定する。たとえば、Web Functions のメモリ課金（環境が存在する間ずっと）が支配的になる低負荷では、Event Functions の方が安くなりうる。

## 2. 比較する構成

| | DB なし | DSQL・毎回接続 | DSQL・接続の共有 |
|---|---|---|---|
| Event + 関数URL | ○ | ○ | ○（環境内で 1 接続を再利用） |
| Web Functions | ○ | ○ | ○（環境内のプールを共有） |

- 6 つの関数と接続の持ち方は [architecture.md](architecture.md) の §3。
- Event のメモリ: 512 MB / 1 GB / 約 3.5 GB。Web は 2 vCPU / 2 GB 固定。**Event の約 3.5 GB は CPU は揃うがメモリは揃わない**。コストの比較ではこの違いを明記する。
- Web の maxConcurrencyPerEnvironment: 64（デフォルト）→ 後で 16 と 128。
- **構成ごとに別の Web Function を作る**。メトリクスにリビジョンの次元がなく、環境系のメトリクス（CPU・メモリ・同時実行）にはエンドポイントの次元もない。動的な同時実行数の上限は関数ごとに学習・保持される。構成を混ぜると、分けて測れず、互いに影響する。
- Event の「接続の共有」は、環境内で 1 接続を再利用する。Event は 1 環境が同時に 1 リクエストしか処理しないので、プールは実質 1 接続になる。これが「Web で共有する効果」と「接続を使い回す効果」を切り分ける対照になる。
- **結果の解釈に影響する要因**: リクエストの変換層が異なる（Web は `IncomingMessage` → `Request`、Event は関数URLのイベント JSON → `Request`）。DB なしの `/noop` で差を把握し、DSQL の結果に注記する。また、コネクタの `AuroraDSQLPool` は取得ごとにトークンを署名する（[findings.md](findings.md) §2-2）ので、接続取得時間（`acquireMs`）に含まれる。

## 3. 負荷パターン
1. 段階的に負荷を上げる定常負荷（上限スループットと、どの制限が先に効くかを見る）
2. ゼロからのバースト（コールドスタート・初期化の 429）
3. アイドル後の単発（スケールインしたあとの最初のリクエスト）
4. 長時間の一定負荷（接続の寿命。DSQL の接続は最長 60 分）

手順上の注意:
- **ウォームアップ回を捨てる**。Web は動的な同時実行数を最初は保守的に置き、学習する（上がるまで 1〜2 分、[findings.md](findings.md) §1-1）。最初の負荷試験は環境が多めになる。同一構成で 2 回以上実行し、2 回目以降を採用する。
- 構成の測定順序を固定せず、ランダム化するか、交互に実行する（時間帯・アカウントの枠の変化の影響を避ける）。
- アイドル後の単発は、環境が回収されるまでの時間より長く空ける。環境の寿命は 4.5〜10.5 分、未使用のものは約 5 分（第三者の観測、[web-functions-notes.md](web-functions-notes.md) §6）。余裕を見て 15 分以上空ける。
- 429 は `lambda-web-error-type` ヘッダで分類する（レート上限・環境数上限・アカウントの vCPU・同時初期化）。同時初期化の 429 はスロットルのメトリクスに出ない。ヘッダの無い 503 は別に数える。
- 負荷は東京の Fargate タスクから実行する（`scripts/load-run.sh`、[architecture.md](architecture.md) §7）。負荷のレートが 1 エンドポイント 10,000 RPS、アカウント全体 100,000 RPS 以下になることを確認する。
- 生成側が飽和していない結果だけを採用する（`loadgenCoresUsed` が `loadgenCoresAvailable` に近いものは捨てる）。
- 毎回接続で DSQL の接続レート（100/秒）に達したら、回避せず結果として記録する。頭打ちの原因が接続レート（53400）なのか Lambda 側の制限（429 など）なのかを区別して記録する。接続エラーはクライアント側とアプリのログの両方で数える。

## 5. コストの計算
- Event: リクエスト数 × リクエスト単価 + 課金時間（GB 秒）× 単価。arm64。関数URLに追加料金はない（未確認）。
- Web: リクエスト数 × $0.30/100 万 + CPU 時間（vCPU 秒）× $0.0000276944 + **環境が存在した時間 × 消費メモリ（GB）** × $0.0000036667。
  - CPU 時間は `EnvironmentCPUTime` の Sum、環境の存在時間は `EnvironmentActiveTime` の Sum で近似する。
  - メモリは環境が存在する間ずっと課金される。アイドル中の環境も課金されるため、負荷パターン（特にバースト後の残り時間）で結果が変わる。
- 上の単価は us-east-1。**東京の単価は AWS Price List API で取得し**、取得日時と属性を [findings.md](findings.md) に記録する（取得済みの値は [findings.md](findings.md) §3-3）。
- 100 万リクエストあたりのコスト = 総コスト ÷ リクエスト数 × 100 万。実測の請求（Cost Explorer）と突き合わせる。
- DSQL の費用（DPU）は両構成で別に集計し、Lambda の費用と分けて報告する。

## 6. 計画に影響する制約
- **アカウントのクォータ**: Web は 400 環境 / 40,000 RPS（使用実績に応じて自動で引き上げられた。当初は 100 環境 / 10,000 RPS。[findings.md](findings.md) §1-3）。ゼロからの急な負荷では、必要な同時処理が小さくても環境が約 200 個に増える（§1-7）ので、クォータは測定の前に確認する。Event の同時実行数も確認する（既定 1,000）。
- **メトリクスにリビジョンの次元がない**。リビジョン別に比較する設計にしない（構成ごとに関数を分ける理由）。
- **DSQL の接続レートは 1 クラスタあたり 100/秒（バースト 1,000）で、引き上げ不可**。最大接続数は 10,000。「毎回接続」の構成は、新規接続が 100/秒を超えるあたりで頭打ちになる可能性が高い。これは仮説を支持する結果だが、スループットの比較には「どの制限で止まったか」を区別して記録する。
- 接続の最長は 60 分。長時間の一定負荷では再接続を含める。
- Web の環境は fd が 1,024 まで。プールの上限と同時実行数の設計に関わる。
- 環境あたりの同時実行数は動的。64 を設定しても 64 にはならない場合がある。`maxInFlight` を実測する。
- エンドポイントごとに 10,000 RPS が上限。それ以上を測る場合は複数エンドポイント（同一関数の最大 10 個）を使うが、構成を混ぜないよう注意する。
- Web のメモリは 2 GB 固定。
- CloudFormation でコードを変えるとリビジョンが置き換わる。比較の途中でコードを変えると、動的同時実行数の学習は関数に残るが、環境は入れ替わる。測定の期間中は Web スタックを destroy しない。

## 7. 段階
全体の目的は §1 のとおり。Web が DB 接続を共有する効果が実際にあるかを、数字で答えること。各段階は、その問いに答えるための準備と測定を順に進める。

| 段階 | やること | 何のためか |
|---|---|---|
| 1 **(完了)** | 調査メモ、この計画、DB なしの `/noop` `/wait`、CDK（Event 1 GB と Web 1 つ、IAM 認証）、動作確認手順 | 比べる土台を作る。DB なしの値は、DSQL を足したときの差を見る基準になる。デプロイ方法・認証・メトリクスの取り方もここで確かめた |
| 2 **(完了)** | DSQL クラスタと、4 つの構成の関数（Event の毎回接続・再利用、Web の毎回接続・プール共有） | 仮説を直接比べる構成を用意する。「Web で接続を共有する効果」と「単に接続を使い回す効果」を切り分けるため、Event にも再利用の構成を入れる。DSQL 側の接続数を測る方法も実機で確かめる |
| 準備（完了） | 負荷生成の仕組み（東京の Fargate タスク） | 手元の WSL からは通信が不安定でレイテンシも使えないので、東京から測る。常設のリソースを持たない |
| 3 | Event のメモリ違い（512 MB / 3.5 GB）、Web の maxConcurrency 違い（16 / 128） | 差が設定の違いによるものではないかを確かめる。Event はメモリで CPU の割当も変わり、Web は 1 環境で同時に処理する数の上限を変えられる。1 つの設定だけで比べると、その設定が有利不利を決めた可能性が残る |
| 4 | 負荷試験（Fargate タスクから `invoke.ts`）、集計、コスト計算 | 仮説に数字で答える。§3 の 4 パターンの負荷を流す。AWS の費用とクォータに影響するため、実行前に費用の見積もり（リクエスト数・並行数・時間、単価と出典、クォータへの影響）を出して承認を得る |

段階 3 は、段階 4 の最初の測定結果を見てから、必要な変種だけを足してもよい。現在の 4 つの DSQL 構成だけでも、中心の問い（Web の共有効果があるか）には答えられる。

## 8. 段階 4 の測定の設計
### 方針
1. **同じ到着レートで比べる（open model）**。並行数を固定する方式（closed model）では、速い構成ほど多くのリクエストを送り、DSQL への負荷が構成ごとに変わる。たとえば「毎回接続」は、接続レートの上限（100/秒）に当たると、失敗が速く返るため、かえって大量に送ってしまう。`invoke.ts` の `--rate` / `--steps` で、構成によらず同じ RPS を送る。遅延は予定した送信時刻から測り、遅れた分を隠さない。
2. **構成は 1 つずつ順番に流す**。DSQL のクラスタ（接続レート、DPU、メトリクス）は全構成で共有なので、並行して流すと互いに影響し、メトリクスも分けられない。
3. **1 回目はウォームアップとして捨て、2 回目を採用する**（Event にも同じ手順を適用して条件をそろえる）。
4. **順序は乱数で決めて記録する**。
5. **失敗の費用を抑える**。`--max-inflight`（生成側の同時リクエスト数の上限）と `--stop-on-error-rate`（失敗率が一定を超えたらその段で打ち切る）を使い、`src/db.ts` はエラーログを間引く（環境ごとに 1 分あたり 20 件まで）。
6. **測定が始まったらコードを変えない**（Web のリビジョンが置き換わり、条件がそろわなくなる）。

### 手順
| 段階 | 内容 |
|---|---|
| A 較正 | A1 生成側の能力（noop に並行 50 を 60 秒。安全に出せる最大 RPS を決める）、A2 失敗時の応答時間（`event-dsql-each` に 300 RPS を 20 秒）、A3 1 リクエストあたりの DPU（`/db/read` を数万件）、A4 `53400` / `53300` の実際の SQLSTATE とメッセージ |
| B P1 段階的な定常負荷 | 25 → 50 → 100 → 200 → 400 → 800 → 1,600 RPS（各 90 秒）。6 構成 × 2 セット（1 セット目は捨てる）。`scripts/run-p1.sh` で、シードつきの乱数順に 1 構成ずつ流す。回の間は 5 分、**「毎回接続」の実行の後は 15 分**あける（接続の枠の回復が遅いため、[findings.md](findings.md) §2-7）。最後に各回のメトリクスを取得する |
| C P2 バースト、P3 アイドル後の単発 | 15 分以上アイドルをあけて、P2 は構成ごとに 400 RPS を 60 秒（1 つずつ順に）、P3 は 6 構成に 1 件ずつ（5 回繰り返す） |
| D P4 長時間の一定負荷 | 4 つの DSQL 構成を並行して、各 25 RPS を 70 分（接続の最長 60 分をまたぐ。25 RPS は、毎回接続 2 構成の合計が接続レートの上限の内側に収まる値） |

### 採用と不採用の基準
- 生成側が飽和した回は捨てる（`loadgenCoresUsed` が `loadgenCoresAvailable` の 60% 超）。
- 予定した送信に 100 ms を超えて遅れた、またはドロップした割合が 5% を超えた段は捨てる。
- 1 回目（ウォームアップ）は捨てる。
- クライアント側の通信エラー（接続タイムアウトなど）が出た回は、原因を調べて、採用するかを判断する。

### データ
- 実行ごとの結果は `results/<日付>/` に保存する（`scripts/load-run.sh --out`）。`.log`（出力）、`.json`（段ごとの集計）、`.meta.json`（タスク ID、時刻、終了コード）。
- CloudWatch のメトリクスは、実行の後に時間帯を指定して取得する（`npm run collect-metrics`）。メトリクスには数分の遅れがある。
- 結果は `docs/report.md` に、結論と根拠を分けてまとめる。

### P1 の状況（2026-10-19）
- セット 1（ウォームアップ）を一度実行し、6 回のうち 2 回で中止した。25〜800 RPS は有効だったが、**1,600 RPS の段で生成側の接続が詰まった**（[findings.md](findings.md) §3-4）。生成側に接続数の上限を設けた。
- 次に、直した生成側で `web-noop` の 1,600 RPS × 90 秒を流して詰まりの解消を確認し、**セット 2 の直前にウォームアップ（セット 1）をやり直す**。測定は、セット 2（と、必要ならセット 3）を採用する。
- 数時間の実行になるので、進行役を AWS 側（Fargate のタスク）に移し、ローカル PC の電源状態や認証の期限に左右されないようにする。

### 段階 A・B0 の結果（2026-10-18）
- 生成側は 2 vCPU で十分（1 コアで約 5,000 RPS、1,600 RPS で 0.41 コア、送信の遅れ 0%）。[findings.md](findings.md) §3-1b
- 「毎回接続」で上限に当たると `53400` で速く失敗する（Lambda の平均 45 ms）。最悪ケースの懸念は解消。使い切った後の回復はドキュメントより遅い。[findings.md](findings.md) §2-7
- DPU は、接続を使い回すと 0.005 / 件、毎回接続で 0.032 / 成功 1 件。仮定の 0.04 より小さい。[findings.md](findings.md) §2-8
- Web のクォータは、当日中に 400 環境 / 40,000 RPS に自動で上がっていた。ゼロからの 400 RPS で環境が約 200 個に増え、環境は負荷の後も約 5 分残って課金される。[findings.md](findings.md) §1-3、§1-7
- 段階 A・B0 の費用の実績は、合計 約 $0.3（見積もり $0.17 + B0 $0.1）。

予想 約 $3.6（これから）、想定の 2 倍で約 $7、上限 $15（超えそうなら止めて相談する）。常設の課金は増えない。

- 単価は [findings.md](findings.md) §3-2 と §3-3（東京、AWS Price List API）。仮定: DSQL は 1 リクエストあたり 0.04 DPU（実績は 0.018〜0.035、段階 A3 で実測に置き換える）、Event の課金時間は reuse 20 ms / each 80 ms / noop 10 ms、Web の CPU は 4〜15 ms/リクエスト。
- **最悪の場合**: 毎回接続が接続レートに当たり、失敗が接続のタイムアウト（5 秒）まで長引くと、Event は同時実行数の上限（1,000）まで課金が膨らむ（1 段 90 秒で最大約 $1.2）。段階 A2 で応答時間を確認し、`--stop-on-error-rate` と `--max-inflight` で抑える。
- クォータ: Web は 400 環境 / 40,000 RPS で、この設計では足りる見込み（ゼロからの 400 RPS で約 200 環境、[findings.md](findings.md) §1-7）。Event の同時実行数は 1,000。DSQL の接続レート 100/秒は引き上げ不可で、毎回接続で意図して超える。
