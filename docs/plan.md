# 測定の設計: Event と Web を、何をどう測って比べるか

**この文書の読み手:** この検証の測り方を知りたい人、同じ測定を再現・拡張したい人。結論は [report.md](report.md)、進め方の記録は [log.md](log.md)、動かし方は [runbook.md](runbook.md)。用語は [用語集](glossary.md)。

## 要旨
- **確かめること:** Web は、1 つの環境で複数の要求を並列に処理するので、待ちの長い処理で Event より有利なはず（コストと環境の数）。
- **測り方:** 実際のアプリに近い 4 つの使い方（ケース A〜D）を、Event と Web に同じ負荷で流す。**ケースごとに、どの上限に先に当たるかを測る前に予測する。**
- **決めてから流すもの:** 版（`build`）の一致、合格基準、予測。結果を見てから基準を変えない。

## 1. 何を確かめるか
Aurora DSQL をバックエンドにしたときの、レイテンシ・スループット・コストを、Event と Web で比べる。

仮説は、Web が 1 つの環境で複数の要求を同時に処理することから出てくる。
1. 接続の確立（TLS と IAM 認証トークンの生成）のコストが減り、レイテンシが下がる。
2. DSQL への接続数と接続レートが減る。
3. I/O の待ちの間は CPU が課金されないので、待ちが長いほどコストが有利になる。

反証される場合も想定する。たとえば、環境が存在する間ずっと課金されるメモリが支配的になる低い負荷では、Event の方が安くなりうる。

## 2. 比べるもの
| 呼び名 | 構成 | 接続の持ち方 |
|---|---|---|
| Event | Event Functions（1 GB）+ 関数URL | 環境ごとに 1 本を使い回す |
| Web（プール 64） | Web Functions（2 vCPU / 2 GB） | 環境内のプールを共有。上限は環境内の同時処理数と同じ（待ちが起きない対照） |
| Web（プール 10） | 同上 | 環境内のプールを共有。上限は 10（node-postgres の既定値で、AWS の記事が推奨するアプリのインスタンスあたり 10〜20 の下限） |

- **構成ごとに別の関数にする。** メトリクスにリビジョンの次元がなく、動的な同時実行数の学習は関数ごとに保持される。混ぜると、分けて測れず、互いに影響する。
- Event に「接続を使い回す」構成を入れるのは、Web の「共有する効果」と「単に使い回す効果」を切り分ける対照のため。Event は 1 環境が同時に 1 要求しか処理しないので、プールは実質 1 本になる。
- 毎回接続する構成は、実際のアプリが採用する実装ではなく、接続レートの頭打ちも測定済みなので、今回は外した（[findings.md](findings.md) §2-7）。
- 今回は、Event は 1 GB のみ、Web は 1 環境の同時処理 64 のみ。メモリ違いと同時処理数違いは、後続に回す。
- 構成名と、コード上の名前の対応は [用語集](glossary.md)。

## 3. どのケースで測るか

### 3-1. ケースは、先に「どの上限に当たるか」を決めてから作る
競合が起きない条件（接続数や同時実行が上限から遠く、クエリが短い固定の 1 文）では、両者の固定のオーバーヘッドしか測れない。そこで、次の 5 つの点のどれかに、Event と Web の一方が先に当たるケースを作る。

| 競合の点 | Event | Web |
|---|---|---|
| アカウントの同時実行数（上限 1,000） | 「RPS × 応答時間」が 1,000 に近づくと 429 | 環境あたり複数を同時に処理する |
| 課金 | 時間 × メモリ（待ちも課金） | CPU 時間 + 環境が存在する間のメモリ |
| 環境内の CPU | 隔離される | 最大 64 要求が 2 vCPU を共有する |
| スケールアウトと DSQL 接続 | 環境 = 同時要求数。環境ごとに 1 本 | 急な負荷で過剰に増える可能性（以前に 400 RPS で約 200 環境） |
| プールの待ち | なし（1 環境 1 要求） | プール上限が環境内の同時 DB 処理数より小さいと発生 |

### 3-2. 4 つのケースと、事前の予測
予測は測る前に固定した。定義は `scripts/protocol.ts`。

| ケース | 処理の内容 | 負荷 | 予測 |
|---|---|---|---|
| A 外部 I/O を待つ API | DB の読み取り → 1 秒待つ → 書き込み | 25・100・400 RPS × 45 秒 | Web の方が環境と DB 接続が少なく、コストが 1/3 以下 |
| B 混在した API | 軽い読み取り 70%、N+1 の画面 15%、重い集計 5%、CPU 処理 5%、書き込み 5% | 50〜400 RPS × 90 秒 | コストは拮抗（±30%）。Web は軽い要求の p99 が悪化するかも |
| C 急なスパイク | 毎秒 10 件 → 1,500 件を 2 分、2 分おいてもう一度 | 30 秒 × 16 段 | 読めない。Web は環境が数百に増える見込み |
| D 重い集計 | 約 250 ms の集計だけ（Web（プール 64）も加える） | 100・200・400 RPS × 45 秒 | プール 10 でプール待ちが出る |

処理のパラメータは、較正で決めて固定した。

| パラメータ | 値 | 決めた根拠 |
|---|---|---|
| 画面の読み取り回数（detail の n） | 11 | p50 35 ms |
| 集計の重さ（report の k） | 800 | クエリ 247 ms、0.58 DPU / 件（k=300 / 450 / 600 / 800 で測った） |
| CPU 処理の仕事量（render の w） | 10,000 | Event（1 GB）で CPU 27 ms、Web で 16 ms |
| 外部 API の待ち（external の ms） | 1,000 | 1 秒 |

ケース D は、集計の DPU が費用の主因なので、段を絞った（同時に DB で動く要求は約 25〜100）。

## 4. どう測るか
1. **到着レートを固定する（open model）。** 並行数を固定すると、速い構成ほど多くの要求を送り、DSQL への負荷が変わる。構成によらず同じ RPS を送り、遅れた分を隠さず、予定した送信時刻から測る。
2. **構成は 1 つずつ順番に流す。** DSQL のクラスタ（接続レート、DPU、メトリクス）は共有なので、並行すると互いに影響し、メトリクスも分けられない。
3. **混在のケースは、同じ要求の列を両方の構成に送る。**
4. **1 つの定義から計画を作る。** 順序と待ちは、seed から再現できる。結果に、計画と版（`build`）が残る。
5. **測定が始まったら、関数のコードを変えない。** コードを先にすべて固め、版を計画に持たせ、起動前と全応答で確かめる。
6. **セット 1 は捨てる。** Web は同時実行数を、最初は保守的に置いて学習する（上がるまで 1〜2 分、[findings.md](findings.md) §1-1）。
7. **同じ関数は、前回の終了から 16 分以上あけてから流す。** 環境が残る時間と、学習の持ち越しを避ける（環境の寿命は 4.5〜10.5 分、[web-functions-notes.md](web-functions-notes.md) §6）。
8. **生成側が足りているかを、流す前に確かめる。** 最大 RPS × 想定の応答時間が、接続数の上限の 6 割、同時実行の上限の 8 割に収まること（[findings.md](findings.md) §3-7）。
9. **DSQL の接続レート（100/秒）に当たったら、回避せず結果として記録する。** 53400（接続レート）と Lambda 側の制限（429 など）を区別する。429 は `lambda-web-error-type` ヘッダで分類する。
10. **測定の前に、較正を流す。** 計測が測定を歪めないことと、各処理の所要時間と DPU を確かめる。

## 5. 何を取るか
| 項目 | Event | Web |
|---|---|---|
| p50 / p95 / p99、到達 RPS | 生成側（東京の Fargate）が測る | 同左 |
| 環境の数 | 応答の `envId` の種類、`ConcurrentExecutions` | 応答の `envId`、`EndpointActiveEnvironments` |
| コールドスタート | 応答の `coldStart`、`REPORT` の `Init Duration` | 応答の `coldStart` |
| アプリ内の時間と DB の内訳 | 応答の `appMs` と `db`（接続取得・クエリ・解放・文の数・プールの待ち） | 同左 |
| CPU・メモリ・課金時間 | `REPORT` の `Billed Duration` | `EnvironmentCPUTime`、`EnvironmentActiveTime`、`EnvironmentMaxMemoryUsage` |
| DSQL 側の接続と費用 | `AWS/Usage` の `CallCount`、`ClusterConnectionCount`、`AWS/AuroraDSQL` の `TotalDPU` | 同左 |
| 版 | 応答の `build` | 同左 |

## 6. コストの計算
- **Event:** リクエスト数 × 単価 + 課金時間（GB 秒）× 単価（arm64）。課金時間は、`REPORT` の `Billed Duration` の合計。
- **Web:** リクエスト数 × $0.30/100 万 + CPU 時間 × 単価 + **環境が存在した時間 × 消費メモリ** × 単価。メモリは、環境が存在する間ずっと課金される（負荷の後の約 5 分も）。
- **DSQL:** DPU × 単価。Lambda の費用と分けて集計する。
- **単価は東京の値**（AWS Price List API。取得日つきで [findings.md](findings.md) §3-2、§3-3 に記録）。**比較は定価で行う**（無料枠を除く。[findings.md](findings.md) §3-8）。

## 7. 採用と合格の基準
**採用しないもの**
- 生成側が飽和した回（コア使用が 60% 超）。
- 予定した送信に 100 ms 超遅れた、またはドロップした割合が 5% 超の段。
- セット 1。
- 応答の `build` が計画と違う回。

**合格基準**（流す前に固定。`scripts/analyze.ts` が判定し、タスクの中でも出力する）

| 記号 | 基準 | 内容 |
|---|---|---|
| a | 計測が測定を歪めない | 較正の `/db/read` の p50 が、以前の測定から ±1 ms 以内 |
| b | 内訳が閉じる | 99.9% 以上の要求で、アプリ内の時間がクライアントの時間以下 |
| c | 生成側が足りている | コア使用 60% 以下、送信の遅れとドロップ 5% 以下、終了コード 0 |
| d | 版が一致する | 全応答の `build` が、計画と同じ |
| e | 件数が一致する | 送信数と、AWS 側のリクエスト数が、0.1% 以内で一致（届かない失敗は除く） |
| f | 再現できる | 2 セットの p50 の差が 2 ms 以内（超えた段は注記する） |
| g | 競合の点に届いた | A は Event の同時実行 320 以上、B は 5 つのエンドポイントを観測、C はスパイクの 95% 以上を送信、D はプール待ちが発生。届かないケースは、結論を保留する |

## 8. 計画に影響する制約
- **アカウントのクォータ:** Web は 400 環境 / 40,000 RPS（使用実績に応じて自動で上がった。[findings.md](findings.md) §1-3）。ゼロからの急な負荷では、必要な同時処理が小さくても環境が増える（§1-7）。Event の同時実行は 1,000（未予約 999）。測定の前に確認する。
- **メトリクスにリビジョンの次元がない。** リビジョン別に比べる設計にしない（構成ごとに関数を分ける理由）。
- **DSQL の接続レートは 1 クラスタあたり 100/秒（バースト 1,000）で、引き上げ不可。** 最大接続数は 10,000、接続の最長は 60 分。
- **Web の環境は fd が 1,024 まで。** プールの上限と同時実行数の設計に関わる。環境あたりの同時実行数は動的で、64 を設定しても 64 にならないことがある。
- **エンドポイントごとに 10,000 RPS が上限。** それ以上は複数のエンドポイントが要る。
- **CloudFormation でコードを変えると、リビジョンが置き換わる。** 測定の期間中は、コードを変えず、Web スタックを destroy しない。
