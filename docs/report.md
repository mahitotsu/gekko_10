# P1 の結果: 段階的な定常負荷（2026-10-19）

> **予備測定（v1）の結果。** 固定の 3 ms のクエリで接続や同時実行が上限から遠く、固定のオーバーヘッドしか測れなかった。測定の定義を作り直したため（[plan.md](plan.md) §8）、この文書は v2 の測定のあとに書き直す。

Event Functions + 関数URL と Web Functions を、Aurora DSQL につないで比べた P1 の結果。測定の設計は [plan.md](plan.md) §8、構成は [architecture.md](architecture.md)、個別に確かめた事実は [findings.md](findings.md)。

P1 は、25 → 50 → 100 → 200 → 400 → 800 → 1,600 RPS（各 90 秒）の定常負荷を、6 構成それぞれに流したもの。P2（バースト）、P3（アイドル後の単発）、P4（長時間）は未実施。

## 1. 結論

### 仮説 1: 接続の共有でレイテンシが下がる — **支持。ただし、Web に固有の効果は小さい**
- 毎回接続に比べて、接続を使い回す構成は p50 が 12〜14 ms 短い（Event 29.1 → 15.7 ms、Web 20.5 → 8.6 ms）。
- 「Web で共有する」効果と「単に使い回す」効果を分けると、後者が主因。DB なしの p50 は Web 6.2 ms、Event 12.1 ms で、差 5.9 ms は DB と関係なく存在する。DB を足した増分は、Event の再利用 +3.6 ms、Web のプール +2.4 ms で、差は約 1 ms。
- p99（50〜400 RPS）も同じ向き: Event 22.7 ms（再利用）/ 42.7 ms（毎回）、Web 13.8 ms（プール）/ 31.0 ms（毎回）。
- 毎回接続は、800 RPS 以上でも p99 が悪化する（Web 190.9 ms、Event 117.4 ms。再利用・プールは 35〜50 ms）。ただし、これは成功した要求だけの値（下の仮説 2）。

### 仮説 2: DSQL の接続数と接続レートが大きく減る — **支持。Event の再利用との差はない**
- 毎回接続は、1 要求につき 1 接続を張る（`CallCount` 285,750 = 送信数。4 回とも一致）。**200 RPS 以上で接続レートの上限（100/秒）に当たり、`53400` で失敗する**。成功は 1 段（90 秒）あたり 8,800〜9,900 件で頭打ちになり（ドキュメントのバースト 1,000 + 100/秒 × 90 秒 ≒ 10,000 と整合）、200〜1,600 RPS の成功率は 6〜55% に下がる（1,600 RPS では約 6%）。
- 共有・再利用では、接続の試行が 1 回あたり 160〜417 件（毎回接続の約 0.1%）。同時接続の最大は 153〜266。
- Web のプールと Event の再利用は、接続の試行（183 / 160 に対し 190 / 417）も同時接続（160 / 153 に対し 166 / 266）も同じ桁。Web が環境内で複数の要求を同時に処理することによる、接続数の追加の削減は、この負荷では見えなかった。
- 失敗は速く返る（Lambda の平均は短い、[findings.md](findings.md) §2-7）ため、失敗した要求のコストは小さい。

### 仮説 3: DB 待ちの間は CPU 課金がほぼ発生せず、コストが有利 — **この負荷では反証。Web の方が約 2 倍高い**
- 1 回（約 28.6 万件）あたりの Lambda + DSQL の費用は、Event の再利用 $0.090、Web のプール $0.171（100 万件あたり $0.31 と $0.60）。DB なしでも Web は約 2 倍（$0.23 に対し $0.46）。
- 差の内訳（Web のプール − Event の再利用）: リクエスト +$0.029（単価 $0.30 と $0.20 / 100 万）、メモリ +$0.048（Event にはない）、CPU・時間 +$0.005。DSQL は同じ（約 $0.014）。
- Web の CPU 課金は、1 リクエストあたり約 2.6 vCPU ミリ秒と小さいが、リクエスト単価とメモリの課金が上回る。
- この負荷は、DB 待ちが約 3 ms（クエリ 2.5 ms 前後）と短い。**DB 待ちが長い（数十〜数百 ms）場合は測っていないので、「待ちが長いほど有利」の部分は未検証**。
- 毎回接続は、成功した要求あたりで見ると高い（成功 100 万件あたり Event $2.17、Web $4.28）が、これは失敗が大半だから。

### その他に分かったこと
- 低い負荷（50〜200 RPS）で、Web の DSQL 構成は環境が多い（pool 4〜13、each 13。Event の DSQL 構成は 2〜6、DB なしは Web・Event とも 2〜3）。原因は未確認（動的な同時実行数が保守的なためという仮説、[findings.md](findings.md) §1-1）。高い負荷（1,600 RPS）の DB なしでは逆で、Web の方が少ない（75〜84、Event 185〜237）。
- 負荷が 800 → 1,600 RPS に倍増する段では、全構成で環境が一気に増える。この段の p99 は他より大きい。

## 2. 条件
- 構成 6 つ（Event: noop / dsql-reuse / dsql-each。Web: noop / dsql-pool / dsql-each）。Event は 1 GB・arm64、Web は 2 vCPU / 2 GB。
- 負荷: 東京の Fargate（2 vCPU）の 1 タスクから、open model（到着レート固定）。段は 7 つ、各 90 秒。順序は seed 20261019 の乱数。回の間は 5 分、「毎回接続」の後は 15 分。
- 実行: 2026-10-19 01:11〜06:37 JST、タスク ID `2874935bcb5140a79a4ffaf6f3e79c33`。18 回（6 構成 × 3 セット）。
- 採用の基準（[plan.md](plan.md) §8）の適用結果: セット 1（ウォームアップ）の 6 回を除外し、セット 2・3 の 12 回を採用した。生成側の使用は 0.12〜0.14 / 2 コア（上限 60%）、送信の遅れは最大 0.2%（上限 5%）、ドロップと未完了は 0、全回の終了コードは 0。**基準で除外した回・段は、セット 1 以外にない**。
- 数値は、特に断らない限り、セット 2 とセット 3 の平均。

## 3. 結果

### 3-1. レイテンシ（ms。50〜400 RPS の p99、全段の p50 はいずれも 50 RPS 以上の平均）
25 RPS の段は、全構成でコールドスタートを含む（p99 が大きい）ので除く。

| 構成 | p50 | p99（50〜400 RPS） | p99（800・1,600 RPS） |
|---|---|---|---|
| event-noop | 12.1 | 19.4 | 39.7 |
| event-dsql-reuse | 15.7 | 22.7 | 49.9 |
| event-dsql-each | 29.1 | 42.7 | 117.4 |
| web-noop | 6.2 | 8.5 | 25.5 |
| web-dsql-pool | 8.6 | 13.8 | 34.5 |
| web-dsql-each | 20.5 | 31.0 | 190.9 |

- レイテンシは、**成功した要求だけ**を、**予定した送信時刻から**測っている。毎回接続の 200 RPS 以上の値は、成功した約 9,000 件の値。

### 3-2. 成功と失敗（毎回接続）
| 構成 | 200 RPS | 400 RPS | 800 RPS | 1,600 RPS |
|---|---|---|---|---|
| event-dsql-each の成功件数（送信 18,000 / 36,000 / 72,000 / 144,000） | 9,942・9,933 | 9,057・9,161 | 9,257・9,176 | 8,896・8,840 |
| web-dsql-each の成功件数（同上） | 9,902・9,937 | 9,029・9,096 | 9,171・8,913 | 8,844・9,398 |

- 失敗はすべて `503 db:53400/connect`（接続レート超過）。それ以外の失敗は、全 18 回で 0 件。
- 他の 4 構成は、全段で全件成功。

| 構成 | 接続の試行 | 最大接続数 | DPU | DPU / 成功 1 件 |
|---|---|---|---|---|
| event-dsql-reuse | 183・160 | 160・153 | 1,358・1,350 | 0.0048・0.0047 |
| web-dsql-pool | 190・417 | 166・266 | 1,376・1,379 | 0.0048・0.0048 |

## 4. 解釈の注意
- **変換層の差**: Web は `IncomingMessage` → `Request`、Event は関数URLのイベント JSON → `Request`。DB なしで p50 が約 6 ms 違う（[plan.md](plan.md) §2）。DSQL の差を見るときは、各系列の noop との差で読む。
- **構成の条件が揃っていない**: Event は 1 GB（CPU は約 0.6 vCPU）、Web は 2 vCPU / 2 GB。メモリ違いの Event（512 MB / 3.5 GB）と、`maxConcurrencyPerEnvironment` 違いの Web は、段階 3 で未実施。
- **1 分粒度の按分**: メトリクスは 1 分粒度で、段は 90 秒。段ごとのコストは、1 分の値を重なる時間で按分した近似。最初の段は、1 分の境界の影響が大きく、参考値。回の合計は、実行を含む分を丸ごと使うので正確（送信数と AWS 側の件数は、18 回とも一致）。
- **Event の時間**: 課金時間は `Duration` + 1 件あたり 0.5 ms（1 ms 単位の切り上げの期待値）で近似した。
- **Web の CPU・メモリ**: `EnvironmentCPUTime`（vCPU 時間）と、`EnvironmentActiveTime` × 環境あたりの平均最大メモリで近似した。請求の実測とは未照合。
- **DSQL のメトリクス**: クラスタ全体の値。各回の終了から 5 分（または次の回の開始）までで区切った。
- **レイテンシ**: 毎回接続の高い RPS では、失敗が大半で、成功の分布は偏る。
- **単一のアカウント・日・リージョンの結果**: 2 セットだけ。セット間の差は小さい（p50 で 1〜2 ms）が、p99 は揺れる（例: 1,600 RPS の Event noop は 91.5 と 26.2 ms）。

## 6. 未確認
- 実際の請求（Cost Explorer）との照合。
- DB 待ちが長い場合のコスト（仮説 3 の「待ちが長いほど有利」）。
- Event のメモリ違い、Web の `maxConcurrencyPerEnvironment` 違い（段階 3）。
- ゼロからのバースト、アイドル後の単発、70 分の長時間（P2〜P4）。
- 800 → 1,600 RPS で環境が一気に増える段の、p99 の詳しい原因。
- 毎回接続の枠が 100/秒に当たったときの Web 側の 429 は、今回は出ていない（`53400` のみ）。
