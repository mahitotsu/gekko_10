# 測定結果（v2）: Event Functions と Web Functions を、実際のアプリの使い方で比べる（2026-10-20）

Aurora DSQL をバックエンドにした Event Functions（関数URL）と Web Functions を、実際のアプリに近い 4 つの使い方で比べた結果。測定の定義と予測は [plan.md](plan.md) §8、構成は [architecture.md](architecture.md)、較正で確かめた事実は [findings.md](findings.md) §3-6。

## 1. 結論

### 1-1. 仮説への答え
**仮説 3（DB 待ちが長いほど、Web のコストが有利）は、支持された。** 待ちが長いほど差が大きい。
- 外部 API を待つ 1 秒の処理（ケース A）: 100 万件あたり Event $14.6、Web $1.2（約 12 分の 1）。Event は待ち時間も課金されるため。
- 250 ms の重い集計（ケース D）: Event $9.3、Web $6.2〜6.3（約 3 分の 2）。
- 平均 17 ms の一般的な API（ケース B）: ほぼ同じ（Event $0.97、Web $0.92）。
- 36 ms の N+1 の画面でスパイクを受けるケース C: Event がわずかに安い（$1.05 と $1.16）。Web は環境の増加分のメモリとリクエスト単価が乗る。

**仮説 2（DSQL の接続数が減る）は、条件つきで支持された。** Web が接続を減らしたのは、リクエストが DB を握らずに長く待つケース A だけだった（DSQL への接続の試行は 1 回あたり Event 約 260 回、Web 約 55 回）。スパイク（ケース C）では、**Web の方が接続が多い**（試行は Event 約 260 回、Web 約 580〜800 回。同時の最大接続数は Event 約 255、Web 約 345）。Web のプールが、環境ごとに複数の接続を張るため。

**仮説 1（接続の共有でレイテンシが下がる）は、今回の測定の範囲外。** 毎回接続の構成は、頭打ちが既知なので外した。Event と Web の差については、次のことが分かった。
- Web は Event より p50 が約 7〜8 ms 短い。**差はすべてアプリの外**（Event 12〜14 ms、Web 5〜6 ms）で、アプリ内の時間（`appMs`）は同じ。
- CPU を使う処理は、Web（2 vCPU）が Event（1 GB）より速い（同じ仕事量で 16 ms と 27 ms）。

### 1-2. 事前の予測との比較
| ケース | 事前の予測 | 結果 | 判定 |
|---|---|---|---|
| A 外部 I/O を挟む API | Web の方が環境と DSQL 接続が少なく、100 万件あたりのコストが 1/3 以下 | 環境は Event 42〜150、Web 3〜4。DSQL 接続の試行は Event 約 260、Web 約 55。コストは約 12 分の 1 | 的中（予測以上） |
| B 混在した一般的な API | コストは拮抗（±30%）。Web は render と report の同居で p99 が悪化する可能性 | コストはほぼ同じ。p50 は Web が約 7〜8 ms 短い。軽いエンドポイントの p99 は Web が長い傾向（400 RPS で item 33.9 ms と 27.0 ms など） | 的中 |
| C 急なスパイク | 読めない。Web は環境が過剰に増える（数百）見込み | 両者とも 1,500 RPS を全件成功（429 なし）。**Web の環境は 21〜101 で、Event（256 で頭打ち、下限値）より少ない** | 外れた（Web の環境は過剰に増えなかった） |
| D 重い集計が主 | pool10 でプール待ちが出る | **的中、しかも劇的**。400 RPS で pool10 が飽和（p50 255 ms → 8.2 秒） | 的中 |

### 1-3. この測定から言える使い分けの目安
この測定の条件（Event 1 GB、Web 2 vCPU / 2 GB、maxConcurrencyPerEnvironment 64、東京、DSQL）での話。
- **DB や外部 API の待ちが長い処理が主なら、Web の方が少ない環境で処理でき、コストも有利**（ケース A、D）。
- **短い処理が主なら、コストはほぼ同じ。Web は p50 が約 7〜8 ms 短い**（ケース B）が、軽いエンドポイントの p99 は Web が長い傾向がある。
- **急なスパイクは、どちらも耐えた**。コストは同程度で、Event がわずかに安い（ケース C）。
- **Web を選ぶなら、プール上限を環境内の同時 DB 処理数に合わせる**。上限 10 のプールは、環境 6 つで同時 60 の DB 処理が上限になり、約 240 RPS で飽和した（ケース D）。Web は、プールが詰まっても環境を増やさなかった。
- **Event を選ぶなら、待ちの長い処理のコストに注意する**。待ち時間も課金され、環境（と DSQL 接続）が同時実行数ぶん増える。

## 2. なぜそうなったか: Event と Web の比較

### 2-1. どの使い方でも共通の差
| 差 | Event（1 GB） | Web（2 vCPU / 2 GB） | 根拠 |
|---|---|---|---|
| アプリの外（クライアントの時間 − `appMs`）の p50 | 11.8〜14.5 ms | 4.7〜7.2 ms | 全ケースで一貫（§3） |
| アプリ内の時間（`/db/read`） | 2.3〜2.5 ms | 2.5〜3.1 ms | 較正（findings §3-6） |
| CPU 処理（同じ仕事量） | 26.9〜28.3 ms | 15.9 ms | 較正、ケース B の `/app/render` |
| 初期化時間（Init Duration）の p50 | 約 206〜215 ms | — | Event の `REPORT` 行 |

Event の 1 GB は CPU が約 0.57 vCPU 分なので、CPU 処理が遅い（原因は推定。メモリを増やした構成は未測定）。アプリの外の差の原因（関数URL と Web のエンドポイントの入口・経路）は、特定していない。

### 2-2. Event が多くの環境・接続・費用を要した理由
- **1 つの環境が同時に 1 つのリクエストしか処理しない**。必要な環境数は「RPS × 応答時間」で決まる。ケース A（1 秒の待ち）は 100 RPS で 145〜150 環境、ケース D（250 ms）は 400 RPS で約 120 環境になった。
- **環境ごとに DSQL への接続が 1 本ずつ**（`reuse`）。環境数に比例して接続の試行が増える（A: 256〜266 回、D: 122〜145 回）。
- **待ち時間も課金される**（時間 × メモリ）。ケース A は 1.03 秒 × 1 GB × $0.0000133334 ≒ $13.7 / 100 万件に、リクエスト $0.20 が乗り、約 $14（DSQL 費用を除く）。
- **コールドスタート**: 環境が増えるぶん増える（A: 1 回あたり 256、C の最初のスパイク: 約 250）。p99 が悪化する（A: 1.6〜1.7 秒、C の最初のスパイクの最初の段: 約 640 ms）。

### 2-3. Web が少ない環境で処理できた理由と、その代償
- **1 つの環境が複数のリクエストを同時に処理する**。ケース A は同じ負荷を環境 3〜4、ケース D は環境 7〜8 で処理した。
- **待ちの間は CPU を課金されない**。ケース A の Web は CPU 費用が $0.0018 / 回（Event の計算費用は $0.25 / 回）。メモリは環境が存在する間の分だけ（$0.003）。
- **代償 1: DB のプールが、環境内の同時 DB 処理の上限になる**。プール上限 10 の環境 6 つは、同時 60 の DB 処理が上限。250 ms の処理なら 6 × 10 ÷ 0.25 ≒ 240 RPS が上限で、400 RPS では飽和した（接続取得の p50 が 0.4 ms から約 870 ms に増え、プール待ちが 41〜45 になった）。Web は環境を 6 のまま増やさなかった。
- **代償 2: 環境内で重い処理と軽い処理が同居する**。ケース B の 400 RPS で、軽いエンドポイントの p99 は Web の方が長い傾向があった（item 33.9 ms と 27.0 ms、detail 88.8 ms と 62.8 ms、write 41.2 ms と 34.2 ms。p50 は Web の方が短い）。2 セットの平均で、傾向としてのみ扱う。
- **代償 3: スパイクで環境を段階的に増やす**。ケース C の Web は、最初のスパイクで 21〜28 環境、2 回目に 70〜101 環境まで増えた。2 回目でも新しい環境（コールドスタート 57〜88）が作られた。
- **代償 4: プールは環境ごとに複数の接続を張る**。ケース C の Web は DSQL 接続の試行が 584〜799 回（Event は 255〜260 回）、ケース D のプール 64 の Web は同時の最大接続数が 150〜234（Event は 119〜122）。

### 2-4. それぞれの限界
| | Event | Web |
|---|---|---|
| 今回の測定で上限に当たった点 | なし。有効な全ての段で全件成功 | プール上限 10 での 400 RPS（ケース D） |
| 予測される上限（未到達） | アカウントの同時実行数（未予約 999）。待ち 1 秒なら約 1,000 RPS で当たる | 環境数・RPS のクォータ（400 環境 / 40,000 RPS）には遠い |
| 費用面の弱点 | 待ち時間の課金、CPU が遅いぶんの課金時間 | リクエスト単価（$0.30 / 100 万件）、環境の存在時間のメモリ（スパイクで効く） |

## 3. ケース別の結果
数値は、セット 2 とセット 3 の平均（または「;」区切りで 2 セット）。セット 1 はウォームアップで捨てた。「アプリの外」は、クライアントの時間から `appMs` を引いた p50。

### 3-1. ケース A: 外部 I/O を挟む API（`/app/external?ms=1000`）
**400 RPS の段は、生成側の接続数の上限（256）に当たって無効**（§4）。25・100 RPS の段のみ使う。

| 構成 | 25 RPS の p50 / p99 (ms) | 100 RPS の p50 / p99 (ms) | 環境数（25 / 100 RPS） | DSQL 接続の試行（1 回あたり） | 100 万件あたりのコスト |
|---|---|---|---|---|---|
| event-dsql-reuse | 1,028 / 1,690〜1,720 | 1,027 / 1,590〜1,610 | 42 / 145〜150 | 256〜266 | $14.59 |
| web-dsql-pool10 | 1,021 / 1,330〜1,430 | 1,019 / 1,030 | 3〜4 / 3〜4 | 53〜63 | $1.23 |

- コストは回の合計（400 RPS の段の途中までを含む）。Event の 1 リクエストあたりの課金は、1.03 秒 × 1 GB で一定。
- Event の p99 の悪化は、コールドスタート（環境 42〜150）による。

### 3-2. ケース B: 混在した API（item 70% / detail 15% / report 5% / render 5% / write 5%）
| 構成 | 50 / 100 / 200 / 400 RPS の p50 (ms) | p99 (ms) | アプリの外 p50 (ms) | 環境数（50 / 400 RPS） | コスト / 100 万件 |
|---|---|---|---|---|---|
| event-dsql-reuse | 18.5 / 18.0 / 17.6 / 17.3 | 264〜270 | 11.8〜13.6 | 20〜31 / 24〜37 | $0.97 |
| web-dsql-pool10 | 11.0 / 10.7 / 10.2 / 9.6 | 257〜263 | 4.7〜6.9 | 2 / 6 | $0.92 |

400 RPS のエンドポイント別（p50 / p99、ms）:

| エンドポイント | Event | Web |
|---|---|---|
| item | 14.8 / 27.0 | 7.8 / 33.9 |
| detail（11 文） | 41.9 / 62.8 | 33.6 / 88.8 |
| report（k=800） | 259.6 / 286.9 | 252.3 / 297.1 |
| render（CPU 処理） | 45.7 / 112.7 | 23.1 / 49.3 |
| write | 20.5 / 34.2 | 13.1 / 41.2 |

- 全体の p99 が約 260 ms なのは、report（250 ms）が 5% を占めるため。
- 50 RPS の段（最初の段）で Web の pool10 に待ちが出た（20〜22）。コールドスタートの直後に、環境 2 つへ要求が集中したため。

### 3-3. ケース C: 急なスパイク（`/app/detail`、10 → 1,500 RPS を 2 回）
| | Event | Web |
|---|---|---|
| 1,500 RPS の段の p50 | 36.9 ms | 28.8 ms |
| 最初のスパイクの最初の段 p99 | 642 ms | 688〜700 ms |
| 2 回目のスパイクの最初の段 p99 | 278〜353 ms | 321〜372 ms |
| 環境数（最初 → 2 回目のスパイク） | 254〜256 → 253〜255（生成側の上限 256 で頭打ち） | 21〜28 → 70〜101 |
| コールドスタート（最初 / 2 回目のスパイク、4 段の合計） | 247〜249 / 0 | 21〜41 / 57〜88 |
| DSQL 接続の試行 / 同時の最大接続数 | 255〜260 / 254〜256 | 584〜799 / 343〜351 |
| 回あたりのコスト | $0.38（リクエスト 0.07 + 計算 0.13 + DSQL 0.18） | $0.42（リクエスト 0.11 + CPU 0.06 + メモリ 0.06 + DSQL 0.18） |

- 429 は出なかった。全段が全件成功。
- **Event の環境数は生成側の上限（256）で頭打ち**で、下限値。接続の試行やコストも、同じ理由で下限になる。

### 3-4. ケース D: 重い集計が主（`/app/report?k=800`、約 250 ms）
| 構成 | 100 / 200 / 400 RPS の p50 (ms) | 環境数（400 RPS） | DSQL 接続（最大 / 試行） | 100 万件あたりのコスト |
|---|---|---|---|---|
| event-dsql-reuse | 260 / 260 / 260 | 約 120 | 119〜122 / 122〜145 | $9.31 |
| web-dsql-pool（上限 64） | 253〜256 / 253〜256 / 253〜255 | 7〜8 | 150〜234 / 215〜220 | $6.24 |
| web-dsql-pool10 | 255 / 255 / **8,219; 8,156** | 6 | プール 10 × 環境 6 / 65〜80 | $6.31 |

- pool10 の 400 RPS の段: 接続取得 p50 が 867〜895 ms、クエリ p50 は 245〜246 ms のまま。プール待ち 41〜45、プールの接続数 10。完了は約 290 RPS で頭打ち。この段は、生成側の同時実行の上限（2,000）にも当たり、予定の約 28% が送信されなかった。**飽和そのものは、接続取得の時間から直接分かる**。

## 4. 条件と採用
- **構成**: event-dsql-reuse（Event、1 GB、arm64）、web-dsql-pool10（Web、2 vCPU / 2 GB、プール上限 10）、web-dsql-pool（ケース D のみ。上限 64）。
- **負荷**: 東京の Fargate（2 vCPU）の 1 タスクから、到着レート固定（open model）。混在のケース B は、同じ要求の列を両方の構成に送った。
- **実行**: 2026-10-20 00:46 JST に起動、05:37 に終了。タスク `e7adbdba…`。27 回（4 ケース × 3 セット）。ビルド `7afe79feb114eee1a4fb3974404dfa72796adbba`（全応答で一致）。
- **採用**: セット 1（ウォームアップ）は捨てた。セット 2・3 を使った。
- **採用しなかった段（有効な回の中の 8 段）**:
  - ケース A の 400 RPS の段（6 つ。全構成・全セット）: 生成側の接続数の上限（256）に当たり、同時実行が足りない。Event と Web の p50 が同じ約 7.9 秒、送信が予定の約 72%、Event の環境数がちょうど 256 であることから分かる。理論上限 256 ÷ 1.03 秒 ≒ 248 RPS と、実測の約 290 RPS（完了数 ÷ 45 秒）も合う。
  - ケース D の pool10 の 400 RPS の段（2 つ）: 飽和により生成側の同時実行の上限に当たった。飽和した事実として §3-4 で扱う。
- **合格基準の判定**（タスクの中の判定と、手元の再現が一致）: (b) 内訳が閉じる、(d) 版の一致、(e) 件数の一致は通過。(c) は上の 8 段で不合格。(f) セット間の p50 の差は、52 段中 27 段で 2 ms を超えた（ケース C が 32 段中 22 段で最大 7 ms、D が 8 段中 4 段、B が 8 段中 1 段。C は Web の環境数がセットで違うため。例: 最初のスパイクで 28 と 21）。(g) ケース A は「Event の同時実行 320 以上」に届かず保留、B・C・D は到達。(a) は較正で通過（[findings.md](findings.md) §3-6）。

## 5. 測定の限界
- **ケース A の競合の点（Event の同時実行の上限）は確かめていない**。400 RPS は生成側の上限で無効になった。仮に有効でも同時実行は 400 で、アカウントの上限（未予約 999）には届かない。上限に当たる様子を見るには、同時実行が 1,000 を超える別の測定（約 1,100 RPS の 1 段）が必要。
- **ケース C の Event の環境数は下限値**（生成側の接続数の上限 256）。
- **2 セットだけ**。セット間の差が大きい段（ケース C）の p50 は、1〜2 ms の差を比べられない。
- **条件の範囲**: Event は 1 GB のみ、Web は maxConcurrencyPerEnvironment 64 のみ。メモリ違いの Event と、同時処理数違いの Web は測っていない。
- **コストは定価での計算値**: CloudWatch のメトリクス（Web）と `REPORT` の課金時間（Event）に単価（東京、[findings.md](findings.md) §3-2、§3-3）を掛けた値。請求との照合で、数量は 0.5% 以内で一致した（Web のメモリだけ 2.2% 少ない）。実際の請求額は無料枠のぶん低い（[findings.md](findings.md) §3-8）。
- **レイテンシは成功した要求だけ**を、予定した送信時刻から測っている。
- **1 日・1 リージョン・1 アカウント**。毎回接続の構成は測っていない。

## 8. 未確認と次の測定
- Event の同時実行の上限に当たる様子（同時実行が 1,000 を超える負荷。Web の挙動も）。
- 生成側の接続数の上限を上げた、ケース A（400 RPS）とケース C の Event の環境数。
- Event のメモリ違い（512 MB / 3.5 GB）、Web の maxConcurrencyPerEnvironment 違い（16 / 128）、Web のプール上限の違い（20 など）。
- 断続的な低頻度、アイドル後の単発、長時間（接続の 60 分の寿命）。
- 毎回接続の構成を、アプリの形のケースで測ること。
