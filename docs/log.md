## 費用の実績

## 決めたこと
| 日付 | 決めたこと | 理由 |
|---|---|---|
| 10-19 | 予備測定の定義（固定の短いクエリ）を捨て、アプリの形のケースに作り直す | 接続も同時実行も上限から遠く、固定のオーバーヘッドしか測れなかった |
| 10-19 | DB は Aurora DSQL を続ける。Aurora Serverless v2（0 ACU）は範囲外 | VPC が必要（Web はネットワークコネクタ）、再開に約 15 秒かかる、$0.15 / ACU・時間（東京）、結果の再現性が低い。別の比較として、後で行える |
| 10-19 | `/app/report` の k を 800 にし、ケース D の段を 100・200・400 RPS × 45 秒に絞る | 約 250 ms の重さにするため。DPU が費用の主因なので、段を絞った |
| 10-20 | ケース C は、1,500 RPS × 120 秒のまま測る | 見積もりは約 $7.2。実績は $6.36 だった |
| 10-20 | ケース A の 400 RPS の測り直しは、今は行わない | 400 RPS でも同時実行は 400 で、Event の上限（未予約 999）には届かないので、測り直しても「Event が耐えられない」結果にはならない。主な結論は、25・100 RPS で出ている |
| 10-20 | 生成側の上限の確認を、計画の段階に入れた（v2.1） | 上限に当たると、その段は生成側を測ってしまい、`lateRate` に出ない |
