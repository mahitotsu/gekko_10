# 検証計画: Lambda Web Functions × Aurora DSQL

何を、なぜ、どう測るか。構成と運用は [architecture.md](architecture.md)、実機で確かめた事実は [findings.md](findings.md)、Web Functions の仕様と出典は [web-functions-notes.md](web-functions-notes.md)。リージョンは ap-northeast-1。

## 1. 目的と仮説
Aurora DSQL をバックエンドにしたときの、レイテンシ・スループット・コストを、Event Functions + 関数URL と Web Functions で比較する。

仮説: Web Functions は 1 つの実行環境で複数リクエストを同時に処理するので、DSQL の接続プールを共有できる。その結果、
1. 接続確立のコスト（TLS + IAM 認証トークンの生成）が減り、レイテンシが下がる
2. DSQL 側の接続数と接続レートが大きく減る
3. I/O 待ちの間は CPU 課金がほぼ発生しないので、DB 待ちが長いほどコストが有利になる

反証される場合も想定する。たとえば、Web Functions のメモリ課金（環境が存在する間ずっと）が支配的になる低負荷では、Event Functions の方が安くなりうる。

## 2. 比較する構成

| | DB なし | DSQL・毎回接続 | DSQL・接続の共有 |
|---|---|---|---|
| Event + 関数URL | ○ | ○ | ○（環境内で 1 接続を再利用） |
| Web Functions | ○ | ○ | ○（環境内のプールを共有） |

- 6 つの関数と接続の持ち方は [architecture.md](architecture.md) の §3。
- Event のメモリ: 512 MB / 1 GB / 約 3.5 GB。Web は 2 vCPU / 2 GB 固定。**Event の約 3.5 GB は CPU は揃うがメモリは揃わない**。コストの比較ではこの違いを明記する。
- Web の maxConcurrencyPerEnvironment: 64（デフォルト）→ 後で 16 と 128。
- Web のプールの上限: 64（環境内の同時処理数と同じ。待ちが起きない対照）と 10（node-postgres の既定値で、AWS の DSQL の記事が推奨するアプリのインスタンスあたり 10〜20 の下限。[architecture.md](architecture.md) §8）。
- **構成ごとに別の Web Function を作る**。メトリクスにリビジョンの次元がなく、環境系のメトリクス（CPU・メモリ・同時実行）にはエンドポイントの次元もない。動的な同時実行数の上限は関数ごとに学習・保持される。構成を混ぜると、分けて測れず、互いに影響する。
- Event の「接続の共有」は、環境内で 1 接続を再利用する。Event は 1 環境が同時に 1 リクエストしか処理しないので、プールは実質 1 接続になる。これが「Web で共有する効果」と「接続を使い回す効果」を切り分ける対照になる。
- **結果の解釈に影響する要因**: DB なしの `/api` 相当でも、Web は Event より p50 が約 6 ms 短い。較正で内訳を測ったところ、**アプリ内の時間は同じ（2.3〜3 ms）で、差はアプリの外（Event 12〜14.5 ms、Web 5.7〜6.3 ms）にある**（[findings.md](findings.md) §3-6）。リクエストの変換（`IncomingMessage` → `Request` など）の差ではなく、関数URL と Web のエンドポイントの入口・経路の差と読む。また、コネクタの `AuroraDSQLPool` は取得ごとにトークンを署名する（[findings.md](findings.md) §2-2）ので、接続取得時間（`acquireMs`）に含まれる。

## 3. ケース（実際のアプリの使い方で、差が出ると予測できるもの）
ケースは、「どの上限に、Event と Web のどちらが先に当たるか」を先に決めてから作る。競合が起きない条件（接続数・同時実行が上限から遠い、クエリが固定の短い 1 文）では、固定のオーバーヘッドしか測れない。

| 競合の点 | Event | Web |
|---|---|---|
| アカウントの同時実行数（上限 1,000） | `RPS × 応答時間` が 1,000 で 429 | 環境あたり複数を同時処理 |
| 課金 | 時間 × メモリ（待ちも課金） | CPU 時間 + 環境が存在する間のメモリ |
| 環境内の CPU | 隔離される | 最大 64 要求が 2 vCPU を共有 |
| スケールアウトと DSQL 接続 | 環境 = 同時要求数。環境ごとに 1 接続 | 急な負荷で過剰に増える（400 RPS で約 200 環境） |
| プールの待ち | なし（1 環境 1 要求） | プール上限 < 環境内の同時 DB 処理数 のとき発生 |

ケースの定義、負荷、予測は §8。共通の手順上の注意:
- **ウォームアップ回（セット 1）を捨てる**。Web は動的な同時実行数を最初は保守的に置き、学習する（上がるまで 1〜2 分、[findings.md](findings.md) §1-1）。
- 構成の順序は、セットごとにシャッフルして記録する（時間帯・アカウントの枠の変化の影響を避ける）。**同じ関数は前回の終了から 16 分以上あけてから流す**（環境が残る時間と、学習の持ち越しを避ける。環境の寿命は 4.5〜10.5 分、未使用のものは約 5 分、[web-functions-notes.md](web-functions-notes.md) §6）。
- 429 は `lambda-web-error-type` ヘッダで分類する（レート上限・環境数上限・アカウントの vCPU・同時初期化）。同時初期化の 429 はスロットルのメトリクスに出ない。ヘッダの無い 503 は別に数える。
- 負荷は東京の Fargate タスクから実行する（[architecture.md](architecture.md) §7）。負荷のレートが 1 エンドポイント 10,000 RPS、アカウント全体 100,000 RPS 以下になることを確認する。
- 生成側が飽和していない結果だけを採用する。
- DSQL の接続レート（100/秒）に達したら、回避せず結果として記録する。53400（接続レート）と Lambda 側の制限（429 など）を区別して記録する。
- **測定が始まったら、関数のコードを変えない**（Web のリビジョンが置き換わり、条件がそろわなくなる）。測定する全部のコードを先に固め、デプロイして、`build` が応答に載っていることを確かめてから流す。

## 5. コストの計算
- Event: リクエスト数 × リクエスト単価 + 課金時間（GB 秒）× 単価。arm64。課金時間は `REPORT` 行の `Billed Duration` の合計で計算する（ない場合だけ、`Duration` + 1 件あたり 0.5 ms の丸めの近似）。関数URLに追加料金はない（未確認）。
- Web: リクエスト数 × $0.30/100 万 + CPU 時間（vCPU 秒）× $0.0000276944 + **環境が存在した時間 × 消費メモリ（GB）** × $0.0000036667。
  - CPU 時間は `EnvironmentCPUTime` の Sum、環境の存在時間は `EnvironmentActiveTime` の Sum で近似する。
  - メモリは環境が存在する間ずっと課金される。アイドル中の環境も課金されるため、負荷パターン（特にバースト後の残り時間）で結果が変わる。
- 上の単価は us-east-1。**東京の単価は AWS Price List API で取得し**、取得日時と属性を [findings.md](findings.md) に記録する（取得済みの値は [findings.md](findings.md) §3-3）。
- 100 万リクエストあたりのコスト = 総コスト ÷ リクエスト数 × 100 万。実測の請求（Cost Explorer）と突き合わせる。
- DSQL の費用（DPU）は両構成で別に集計し、Lambda の費用と分けて報告する。

## 6. 計画に影響する制約
- **アカウントのクォータ**: Web は 400 環境 / 40,000 RPS（使用実績に応じて自動で引き上げられた。当初は 100 環境 / 10,000 RPS。[findings.md](findings.md) §1-3）。ゼロからの急な負荷では、必要な同時処理が小さくても環境が約 200 個に増える（§1-7）ので、クォータは測定の前に確認する。Event の同時実行数も確認する（既定 1,000）。
- **メトリクスにリビジョンの次元がない**。リビジョン別に比較する設計にしない（構成ごとに関数を分ける理由）。
- **DSQL の接続レートは 1 クラスタあたり 100/秒（バースト 1,000）で、引き上げ不可**。最大接続数は 10,000。「毎回接続」の構成は、新規接続が 100/秒を超えるあたりで頭打ちになる可能性が高い。これは仮説を支持する結果だが、スループットの比較には「どの制限で止まったか」を区別して記録する。
- 接続の最長は 60 分。長時間の一定負荷では再接続を含める。
- Web の環境は fd が 1,024 まで。プールの上限と同時実行数の設計に関わる。
- 環境あたりの同時実行数は動的。64 を設定しても 64 にはならない場合がある。`maxInFlight` を実測する。
- エンドポイントごとに 10,000 RPS が上限。それ以上を測る場合は複数エンドポイント（同一関数の最大 10 個）を使うが、構成を混ぜないよう注意する。
- Web のメモリは 2 GB 固定。
- CloudFormation でコードを変えるとリビジョンが置き換わる。比較の途中でコードを変えると、動的同時実行数の学習は関数に残るが、環境は入れ替わる。測定の期間中は Web スタックを destroy しない。

| 段階 | やること | 何のためか |
|---|---|---|
| 1 **(完了)** | 調査メモ、この計画、DB なしの `/noop` `/wait`、CDK（Event と Web、IAM 認証）、動作確認手順 | 比べる土台を作る。デプロイ方法・認証・メトリクスの取り方もここで確かめた |
| 2 **(完了)** | DSQL クラスタと、毎回接続・再利用・プール共有の構成の関数 | 仮説を直接比べる構成を用意する。DSQL 側の接続数を測る方法も実機で確かめた |
| 準備（完了） | 負荷生成の仕組み（東京の Fargate タスク） | 手元の WSL からは通信が不安定でレイテンシも使えないので、東京から測る。常設のリソースを持たない |
| 予備測定（完了、コミット 5a769a1） | 3 ms の固定クエリの段階的な定常負荷を 6 構成で測った | 競合が起きない条件で、固定のオーバーヘッドしか測れなかった。そのため測定の定義を作り直した（§8）。毎回接続の頭打ち（接続レート 100/秒）と、生成側の接続の詰まりの解消は、ここで確かめた（[findings.md](findings.md)） |

## 8. 測定の設計
### 方針
1. **同じ到着レートで比べる（open model）**。並行数を固定する方式（closed model）では、速い構成ほど多くのリクエストを送り、DSQL への負荷が構成ごとに変わる。`invoke.ts` の `--rate` / `--steps` で、構成によらず同じ RPS を送る。遅延は予定した送信時刻から測り、遅れた分を隠さない。
2. **構成は 1 つずつ順番に流す**。DSQL のクラスタ（接続レート、DPU、メトリクス）は全構成で共有なので、並行して流すと互いに影響し、メトリクスも分けられない。
3. **混在のケースでは、同じ要求の列を両方の構成に送る**。パスは seed・ケース・セットから決まる（構成には依らない）。
4. **1 つの定義から計画を作る**。測定の定義は `scripts/protocol.ts`、計画は seed から再現できる（順序と待ち）。結果のファイルに、計画と、応答に載った版（`build`）が残る。
5. **測定が始まったらコードを変えない**。関数のコードを先にすべて固め、`build`（最後に変えたコミット）を計画に持たせ、起動前と全応答で確かめる。
6. **合格基準を、流す前に決める**（下記）。

### ケース（定義は `scripts/protocol.ts`。予測は測る前に固定する）
構成は event-dsql-reuse と web-dsql-pool10 が基本（ケース D だけ web-dsql-pool も）。毎回接続は、実際のアプリが採用する実装ではなく、頭打ちも測定済みなので外す。

| ケース | 中身 | 負荷（段 × 秒） | 予測 |
|---|---|---|---|
| A 外部 I/O を挟む API | `/app/external`: 主キーの読み取り → 1,000 ms の待ち（外部 API・LLM の代わり）→ INSERT。待ち中は接続を返す | 25・100・400 RPS × 45 秒 | 同時実行は 25〜400。Web の方が環境と DSQL 接続が少なく、100 万件あたりのコストが 1/3 以下。Event は待ち時間分を課金される |
| B 混在した一般的な API | 重みつきの混在: `/app/item` 70%、`/app/detail` 15%（N+1 で 11 文）、`/app/report` 5%（重い集計）、`/app/render` 5%（CPU 処理）、`/app/write` 5% | 50・100・200・400 RPS × 90 秒 | コストは拮抗（±30%）。Web は render と report が同居して p99 が悪化する可能性がある。エンドポイント別に見る |
| C 急なスパイク | `/app/detail`。10 RPS → 1,500 RPS を 2 分、2 分おいてもう一度（1 回目は冷えた関数、2 回目は暖かい関数） | 30 秒 × 16 段 | 結果は読めない。Web は環境が過剰に増えて（数百）コストと DSQL 接続が増える。Event は同時実行が「RPS × 応答時間」に近い。429 とコールドスタートを比べる |
| D 重い集計が主 | `/app/report`（k=800、約 250 ms）のみ（web-dsql-pool も加える） | 100・200・400 RPS × 45 秒 | DB を握る同時数が環境あたり 10 を超え、**pool10 でプールの待ちが出る**（pool64 では出ない） |

- 較正（`--suite calibration`）のケース: K（`/db/read`。計測が測定を歪めないことの確認）、Q1〜Q5（各エンドポイントを単独で 20 RPS × 60 秒。所要時間と DPU の測定）。
- パラメータ（`/app/detail` の n、`/app/report` の k、`/app/render` の w、`/app/external` の ms）は、較正で決めて `scripts/protocol.ts` に固定する。決めた値: n=11（p50 35 ms）、k=800（クエリ 247 ms、0.58 DPU / 件）、w=10,000（Event 1 GB で CPU 27 ms、Web で 16 ms）、ms=1,000。k は 300 / 450 / 600 / 800 で測った（クエリ 39 / 82 / 141 / 247 ms、DPU 0.17 / 0.26 / 0.39 / 0.58）。ケース D は、重い集計の DPU が費用の主因なので、段を 100・200・400 RPS × 45 秒に絞った（同時に DB で動く要求は約 25〜100）。

### 手順
1. コードと文書を変える（AWS には触れない）。`npm test`、`npm run typecheck`、`cdk synth`、`cdk diff`。実クラスタにつないだ単体起動で新しい SQL を確かめる。生成側を変えたら、本番と同じ件数の最終段までローカルで通す。
2. コミットして、デプロイする（`cdk diff` を見せて承認）。
3. 較正を流す（少数のリクエスト）。合格基準 (a)・(b) を確かめ、パラメータと DPU を決める。
4. 決めた値をコミットし、`suite-start --dry-run` で費用を見積もり、承認を得て起動する。以降、PC を閉じてよい。
5. 回収し、`npm run analyze` で同じ結果を再現し、合格基準を判定する。通れば `docs/report.md` に結論と根拠を分けて書く。測定後に `events` を消す。翌日、Cost Explorer で請求と照合する。

### 採用と不採用の基準
- 生成側が飽和した回は捨てる（`loadgenCoresUsed` が `loadgenCoresAvailable` の 60% 超）。
- 予定した送信に 100 ms を超えて遅れた、またはドロップした割合が 5% を超えた段は捨てる。
- 1 回目（セット 1。ウォームアップ）は捨てる。
- 応答の `build` が計画と違う回は捨てる。
- クライアント側の通信エラー（接続タイムアウトなど）が出た回は、原因を調べて、採用するかを判断する。

### 合格基準（流す前に固定。`scripts/analyze.ts` が判定し、タスクの中でも出力する）
- (a) 計測が測定を歪めない: 較正の `/db/read` の p50 が、予備測定（コミット 5a769a1）の値から ±1 ms 以内（event-dsql-reuse 15.7 ms、web-dsql-pool 8.6 ms。50 RPS 以上の平均）。外れたら止まって調べる。
- (b) 内訳が閉じる: 各要求で `appMs ≤ 客側の時間`（99.9% 以上）。
- (c) 生成側のコア使用 60% 以下、送信の遅れとドロップ 5% 以下、終了コード 0。
- (d) 全応答の `build` が、計画の期待値と一致する。
- (e) 送信数 = Event の `Invocations`・Web の `ExecutedRequests`（プラットフォームに届かない失敗は除く。0.1% 以内）。
- (f) 採用 2 セットの p50 の差が 2 ms 以内（超えた段は注記する）。
- (g) 予測した競合の点に到達した: A は Event の同時実行が 320 以上、B は最終段で 5 つのエンドポイントを観測、C はスパイクの段で送信が予定の 95% 以上、D は pool10 でプール待ち（`pool.waiting > 0`）。到達しないケースは、結論を保留する。

### データ
